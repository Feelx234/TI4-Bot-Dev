## 🐛 Bugs

### 1. `deriveChoiceRendererModel` spectator guard bypassed at the call site

`ChoiceRendererDispatcher` calls:
```ts
const derivedModel = useMemo(() => {
  return choice ? deriveChoiceRendererModel(choice, choice.actor) : null;
}, [choice]);
```
But `deriveChoiceRendererModel` has a hard guard:
```ts
if (!choice || !viewerSeat || choice.actor !== viewerSeat) return null;
```
The dispatcher hard-codes `choice.actor` as the viewer, bypassing the spectator check. Spectators always get `null` and fall back to `generic_selection`. The guard's intent is never exercised by this caller — latent bug for any future caller that passes a real `viewerSeat`.

---

### 2. Dual classify implementations will drift (`deriveChoiceRendererModel` vs `classifyChoiceWorkflow`)

`classifyChoiceWorkflow` is ~70 lines duplicating every `if/else` from `deriveChoiceRendererModel`. There is no shared classify helper. The `'objective_scoring'` workflow exists in `ChoiceWorkflowKind` but is absent from **both** classifiers and will never be emitted.

---

### 3. `handleConfirmSustain` misused for the retreat stage in `CombatResolutionModal`

```tsx
// Retreat options:
onClick={() => handleConfirmSustain(opt.id)}
```
The handler is named and documented as sustain-specific. Using it for retreats works today because the implementation is generic, but any future specialization of `handleConfirmSustain` (e.g. sustain confirmation dialog) will silently break the retreat path.

---

### 4. Unstable `submitChoice` reference in `usePipelineRunner` effect dependencies

```ts
}, [pendingChoice?.nonce, isRunning, activeQueue, submitChoice]);
```
If the parent recreates `onSubmit` on every render (common), the effect fires mid-run. `isSubmittingRef` prevents double-submit but silently drops the next intent while a submission is in flight. Fix: wrap `submitChoice` in a ref inside the hook (`const submitRef = useRef(submitChoice); submitRef.current = submitChoice;`).

---

### 5. `AgendaBallotModal` — `planetName` is set to the raw backend option ID

```ts
planetName: opt.id,   // e.g. "exhaust|mecatol_rex"
```
The card renders `planet.planetName`; users see raw IDs whenever `opt.label` is empty.

---

### 6. `tradeDecoder` — prefix overlaps produce silent misclassification

An id like `"c2:0"` misses `id.startsWith('cc')` (case 5) and falls through to the `id.startsWith('c') && id.includes(':')` gift branch (case 8) — correct. But `"ct3:2"` hits `id.startsWith('ct')` (case 6) while also matching `id.includes(':')` (cases 8, 9). Priority is correct by line order but there are zero tests for conflict paths. A future reorder or new prefix silently changes behaviour.

## 🔴 Hacky Solutions

### 7. ~600 inline `style={{…}}` objects bypass the existing CSS class system

Every component uses `style={{}}` on every element. This:
- Creates a new object on every render (minor perf cost × 8 components with deep trees).
- Is invisible to CSS media queries and CSS variables — responsive theming is impossible without editing TS.
- Overrides the `button--primary`, `card--selected`, `panel` class system already present.

---

### 8. Magic z-index integers with no ledger

```ts
zIndex: 9999  // ReactionStatusBar
zIndex: 9000  // ProductionBuilderDrawer
zIndex: 1000  // minimized pill
zIndex: 25    // TacticalMovementOverlay
```
One new modal at `z-index: 10000` silently buries the reaction bar. No shared constants, no stacking-context document.

---

### 9. Planet names parsed from pipe-encoded option IDs in `PaymentDrawer`

```ts
const planetName = opt.id.replace('exhaust|', '').split('|')[0] || opt.label;
```
Fragile string-split on an implicit backend convention. Any engine ID format change silently corrupts display names. `getPaymentPayload` should surface a `planetName` field from `payload`.

---

### 10. Hard-coded unit capacity heuristics in `TacticalMovementOverlay`

```ts
const capacityPerUnit = p.capacity ??
  (unit.includes('carrier') ? 4 : unit.includes('dreadnought') ? 1 : 0);
```
Carrier capacity varies by faction tech (Nomad's Memoria: 3+). Dreadnought capacity varies (Nekro, Titans). These magic numbers will give wrong fleet gauges the moment any faction-modified unit appears. The engine payload already carries `capacity`; the `??` fallback should be `0`, not a hardcoded guess.

---

### 11. Auto-pass countdown in `ReactionStatusBar` races with `isSubmitting`

When `secondsRemaining` hits 0, `handleAction` fires. If the network call takes >1 s, the countdown effect re-runs (`isSubmitting` changes), sees `secondsRemaining <= 0` again, and calls `handleAction` a second time. The inner `if (isSubmitting) return` guard catches it, but the effect fires redundantly and `setIsSubmitting(true)` runs again. The fix is to clear `secondsRemaining` to `null` immediately after triggering auto-pass.

## 🟡 Missing Obvious Abstractions

### 12. No `<WorkflowShell>` base component

Every workflow component (`PaymentDrawer`, `AgendaBallotModal`, `CombatResolutionModal`, `TradeDeskModal`, `ProductionBuilderDrawer`) independently implements:
- Spectator notice (`!isActor` block) — 5×
- `isDirectSubmitting` state + nonce-reset `useEffect` — 5×
- `declineOption` extraction (same `model?.declineOption ?? choice?.options.find(…)` — 5×
- Error banner (`lastError` div) — 6×

A `<WorkflowShell choice model viewerSeat onSubmit lastError>` wrapper would eliminate ~200 lines of near-identical code.

---

### 13. No `useDeclineOption` / `useNonceReset` hooks

The pattern:
```ts
const declineOption = useMemo(() => {
  return model?.declineOption ?? choice?.options.find(
    (o) => o.id === 'decline' || o.kind === 'decline'
  ) ?? null;
}, [choice, model]);
```
is copy-pasted verbatim across 5 components. Same for the nonce-reset effect. These belong in shared hooks.

---

### 14. `ChoiceRendererDispatcher` if-chain should be a registry

The dispatcher has 8 `if (workflow === '…')` arms. Every new workflow requires editing 4 places:
1. `ChoiceWorkflowKind` union
2. `deriveChoiceRendererModel`
3. `classifyChoiceWorkflow` (duplicate)
4. `ChoiceRendererDispatcher`

A `Map<ChoiceWorkflowKind, ComponentType<WorkflowProps>>` registry + a single shared classifier would reduce this to one registration per new workflow.

---

### 15. `tradeDecoder` has no conflict/edge-case tests

9 decode paths decided by ID prefix heuristics, but the test file covers only clean happy-path ids. Missing tests for:
- An id matching multiple prefix branches simultaneously
- Payload fields contradicting the prefix (e.g. `id: "pn_sol"` + `payload.swap_commodities = 2`)
- Unknown id format → `category: 'other'` fallback correctness

---

### 16. `SemanticIntent.kind` is set by every caller but never read by the hook

```ts
export interface SemanticIntent {
  kind: 'movement' | 'casualty' | 'payment' | 'selection'; // ← never consumed
  predicate: (option: ChoiceOptionDto) => boolean;
  description: string;                                      // ← also never surfaced
}
```
`usePipelineRunner` only uses `predicate`. Either use `kind` for logging/tracing, or remove it to avoid the false impression that the hook does type-aware dispatch.

---

### 17. Tech specialty is a raw `string | null` with no enum

`boardPresentation` returns `techSpecialty` as a freeform string. Tech specialties (`'biotic'`, `'propulsion'`, `'cybernetic'`, `'warfare'`) are a closed TI4 domain set; a TypeScript union type or enum would catch typos at compile time and enable exhaustive switches.
