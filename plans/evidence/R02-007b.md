# R02-007b - the replayer window

## Scope and acceptance

Parent package R02-007 (split in `R02-007a.md`): an operator can open a recorded R01 session, fork it at
any frame, take over a seat, and play. Child (b), this package, is the shell: an eframe window that calls
`ReplayApp` and decides nothing itself. Child (a) was the reducer; every rule behind a widget
(button-disabled-after-submit, navigation-is-not-branching, tooltip-when-Play-is-refused, safe-close-while-
rebuilding, separate settings) is decided in `src/app.rs` and tested in `tests/app.rs`.

Operator acceptance - "open a recorded session, fork at any frame, take a seat, play" - is what
`crates/ti4-replayer/tests/shell.rs` walks without a display. What is *not* covered here is how it looks:
see "What this package does not prove" below.

## What was added

| File | Role |
| --- | --- |
| `crates/ti4-replayer/src/gui.rs` | the window: top bar, board, timeline, branch list, seat chips, manual-choice panel, rebuild progress and cancel, Play with per-refusal tooltips |
| `crates/ti4-replayer/src/main.rs` | `ti4-replayer [session-or-project]` opens the window with a file in it; `inspect <project>` and `import <session>` at the terminal |
| `crates/ti4-replayer/src/store.rs` | what the window can draw per branch: header-once, frames deduped by index, an LRU ceiling on how many branches are held, plus `ticks`, `own_answers` and `fold_answers` |
| `crates/ti4-replayer/tests/shell.rs` | the operator's journey, headless: open, seats, navigate, fork, rebuild, take a seat, answer, keep playing, save, reopen |
| `crates/ti4-replayer/tests/feed.rs` | the frame feed against the real engine, including fork-rebuild-then-play and a recording that lies |

Library changes it needed, all additive:

- `live.rs`: a bounded **frame feed** on the `Gate` (`attach_feed`/`take_feed`, header published once,
  oldest frames dropped and counted when a window falls behind), `LiveEvent::Rebuilt`, `ReplayRequest`,
  `LiveBranch::replay` (rebuild the prefix, then stay answerable on the same thread), `Gate::replaying_interactive`,
  and recording failure counters.
- `rebuild.rs`: `rebuild_with_gate`, so a rebuild can run on the thread that will keep playing; `rebuild()`
  now delegates to it.
- `project.rs`: `ReplayInputs::from_manifest`/`simulation_config`, `import_with` (a session the caller already
  loaded - they are hundreds of megabytes), and `answers_from_session`.
- `persistence.rs`: `sha256_path`, which digests a *bundle* as well as a file.
- `app.rs`: `impl<H: BranchHandle> BranchHandle for Arc<H>`.
- `ti4-review` was not touched in this package beyond what `R02-006e` had already given it; the window draws
  through `view::board_view` + `view::BoardLayout` + `view::draw_board`, so its board is R01's board stroke
  for stroke.

## The decision that shaped the shell

`LiveReview` is not `Send` (`Rc<RefCell<..>>`, `Box<dyn Decider>`), so **the window can never hold the
game**. One thread owns each branch's `LiveReview`; what crosses into the UI is frames. Frames are cloned
out of the branch thread through a bounded feed and dropped-when-stale rather than backpressuring the
engine: a window that is not keeping up loses pictures, never legality. Measured on a real 4,481-frame
operator session: 465 MB of session, ~200 KB per frame projected, and the window holds an LRU set of
branches rather than every branch at once.

## Five real bugs, found by the headless shell test before any pixel was trusted

1. **Opening a session left the reducer blind.** Both open paths filled the *store* (which can draw a
   frame) and never told the *reducer* (which knows how many there are and which one is being looked at).
   The timeline had nothing to move and `plan_play` answered `NoFrame` forever - i.e. Play would have been
   dead on arrival in the window. Fixed with `Store::ticks` plus `ReplayApp::record_frames` at both open
   paths. `tests/shell.rs::a_recording_opens_with_the_game_and_navigation_is_not_branching` fails without it.
2. **An imported recording carried no answers at all.** `ReplayerProject::import_with` copied inputs,
   hashes and frame counts but no decisions, so "Play from this frame" on a real R01 session would have
   rebuilt a prefix *out of nothing*: a fresh policy play that happens to look like the game on the screen,
   then marked verified and playable. That is the exact promise R02-004 exists to keep. Fixed with
   `answers_from_session`, which turns each recorded decision into a `ReplayRecord` (actor, prompt, offered
   options in engine order with their kinds, the chosen id, the typed context, the recomputed fingerprint) -
   5,119 answers for the 4,481-frame session used in the smoke run. A recording that claims it settled on an
   option it never offered is refused outright rather than half-imported.
   Tests: `an_imported_recording_carries_its_own_answers_and_survives_the_round_trip`,
   `a_recording_that_settles_on_an_option_it_never_offered_is_not_a_recipe`.
3. **The import could not be reopened.** The first version wrote the answers straight into the branch, so
   the file carried the checksum of the answer-less project. `load_project` on a file this build had just
   written said `checksum is 7109967..., expected 218c454...`. Diagnosis: the payload round-trips
   byte-identically (checked by re-serialising and diffing 2.3 MB), so the digest was stale at write time,
   not unstable at read time. Fixed by taking `extend` - the mutation that already re-runs the frame budget
   and recomputes the checksum - instead of assigning fields. The regression test is the save/load half of
   test 2 above; the earlier R02-005 tests could not have caught it because their sessions had no decisions.
4. **A fork stole the operator's seat.** `Gate::replaying` is deliberately non-blocking - a headless rebuild
   has nobody to ask, so a manual ask falls back to the policy and is counted. A fork is not headless: it is
   the thing the window then plays on. With a seat set to Manual, every decision from the fork frame
   onwards was answered by the policy, and the `debug_assert!` that guards that fallback panicked the branch
   thread in a dev build. Fixed with `Gate::replaying_interactive`: the prefix keeps priority (and a
   mismatched prefix is still refused), but when it runs out a manual seat parks and waits for the person in
   front of the screen.
5. **A hand answer could be lost by saving too soon.** The record of a parked answer was written by the
   *engine* thread after the panel had already closed, so a Save - including the save-on-quit path - that
   ran between "the panel closed" and "the answer was written" silently saved a branch missing the
   operator's last move. Reproduced deterministically in `tests/shell.rs` (the frame-8 answer was on screen
   and accepted, `dropped_records` was 0, and the file simply did not have it). Fixed by recording in
   `Gate::submit`, on the thread that accepted the click, from the offer it is about to release. The gate now
   also counts and remembers anything it fails to record (`dropped_records`, `last_record_failure`), because
   a branch whose record is quietly short of a decision must not be allowed to save as something it is not.

## Checkpoint bundles

The operator's checkpoints are often MLP inference bundles - a directory holding `slots.json` beside four
`.safetensors` files - and R01 records *the directory* as the checkpoint. `sha256_file` did `fs::read`, so
importing such a session failed with Windows "Access is denied", reported through `ProjectError::Io` whose
text said "cannot write" for a read. `sha256_path` digests a directory as its sorted recursive listing under
a `dir:` marker (so a file and a directory can never agree, and an entry added, removed, renamed or edited
never agrees either), and the `Io` text is now direction-neutral: "the file system refused {path} because
{source}". Four unit tests in `persistence.rs` attack exactly that, including the rename case.

## What this package does not prove

- **Nobody has looked at the pixels.** The assistant cannot see screenshots, so the smoke run proves the
  window constructs, paints without panicking, remembers its settings and exits cleanly - it does not prove
  the layout reads well or that the board is legible next to the branch list. The operator's pass is still
  required; `cargo run -p ti4-replayer out/replays/autosave-1-rotation2-learner.r02.json.zst` opens the
  session above directly.
- **A branch that is not live shows its shape, not its frames.** A project stores frame *counts*, so
  selecting an old branch in the tree gives title/fork/verified/playable and a Play button, not a board.
  The status line says so. Making every branch drawable would mean storing every branch's frames, which
  R02-005 rejected deliberately.
- `Gate::stop()` still sets the stopped state from outside the branch thread, so "stopped" does not strictly
  mean "the engine is between steps". Recording at `submit` is what makes that safe for saving; changing
  `stop`'s state machine would be an R02-003 behaviour change and was not taken here.
- R02-006d (`player_panel`) was not extracted. The replayer's player sheet is composed from the `view::`
  primitives that 006a-006c already provide; R01's 600-line panel is untouched.
- Pre-existing workspace failures are unchanged and unrelated: `ti4-bridge` `hexsummary_golden`,
  `import_golden`, `wire_golden` (missing committed golden corpora) and `ti4-mlp --test smoke_refusals`
  (needs a generated vocabulary). No fixtures were invented for them.
- No review tier was performed (waived by the operator on 2026-09-18); the compensating control is the
  evidence above and the 10 + 4 new engine-backed tests.
