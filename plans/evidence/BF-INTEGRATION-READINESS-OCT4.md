## Readiness and bounded order

BF-20 is not ready to land while the four printed-asset gaps remain and the WIP faction changes have not passed their required focused review and validation. The current source of truth is still `seating::IN_SCOPE_FACTIONS: [&str; 6]`; `seat_in_scope` assigns round-robin and repeats after six. Widening it changes setup and all consumers that derive their seats from that function, as the plan warns.

The dependency-ready work is to close the four faction asset packages below and accept the pending shared timing/production/combat routes. Keep BF-20 onward separate and serialized, with exact owned file lists and saved before/after artifacts:

1. **BF-20 — seat roster integration.** Change the single engine roster to the twelve base/PoK factions plus the ten already in-scope factions (18 total), only after all twelve package ledgers and critical route tests pass. Add tests for exactly 18 unique selectable aliases, content-backed deployability, and the intended six-player no-duplicate policy. Inventory consumers before editing: the battle-policy parity test currently deliberately asserts `FACTIONS` equals seating, while `ti4-mlp` examples contain many independent six-entry `FACTIONS` constants. Do not bulk rewrite historical/specialized dataset definitions; classify each consumer by whether it is an active current-rollout path, and retain the six-faction policy only where the data contract explicitly intends it.
2. **BF-21 — deterministic assignment.** `seating.rs` currently has no seeded faction draft/random selector; its only selector is round-robin `seat_in_scope`. Add a bounded seeded selector with a domain-separated RNG stream, defined duplicate behavior for table sizes below/equal/above 18, and tests for same-seed identity, different-seed variation, full coverage, and no accidental duplicate faction seats in a standard six-player game. Keep map-tile seeding and faction-selection seeding independent.
3. **BF-22 — battle arena, model schema, and vocabulary.** The policy roster is `ti4-policy/src/battle.rs::FACTIONS` (six entries), with current battle `FEATURE_VERSION = 4` and supported predictor versions `[1..=7]`; the arena itself also has a distinct six-entry `Profile::CATALOGUE` in `ti4-training/src/battle_arena.rs`. Widen both only with explicit tests for each new faction’s battle effect/profile, bump the battle feature/schema version as BF-22 requires, and make old predictors follow an explicit compatibility/migration policy rather than silently interpreting new faction identities. `features.rs` already derives six faction-decomposition fact families from faction content (abilities, starting/faction tech, starting units, home planets, commodities), so census those families for all 18 after seating is widened and assert all required names enter the built vocabulary. The `battle_factions_matches_the_seated_factions` parity assertion is the first expected red gate after BF-20.
4. **BF-23 — integrity re-baseline.** The existing `ti4-sim/examples/rebaseline_behavior.rs` recomputes the recorded behavioral bounds from fixed `behavior::play_batch`; its header requires old/new side-by-side evidence and a separately reviewed source change. Run only after BF-20/21 changes are accepted. Save baseline/new metrics and per-seed completion/replay identity, describe changed authored-bot outcomes, and do not move bounds automatically or collapse this into the 18-faction soak.
5. **BF-24 — option/manual presentation.** Engine decisions flow through generic `Choice` records and `DecisionContext`; review serializes prompt, option label/id/payload/context and renders a generic option card. Replayer `ControlledDecider` parks every `Choice` for a manual seat and validates the exact option against its fingerprint. That generic UI is useful infrastructure, not proof of faction-specific clarity. Generate the decision-delivery inventory after final engine hooks, enumerate every new decision context/source/subtype and every faction option family, then add rendered-option assertions plus at least one live park/answer/resume fixture per new decision kind. Prioritize map-target choices, payment/resource choices, leader/hero/BT menus, exploration/invasion/combat choices, and borrowed-agent windows. Confirm labels/payloads identify planet/system, cost, owner, and consequence without depending on opaque ids.
6. **BF-25 — exit gate.** Run the full workspace suite and the agreed 18-faction all-pairs seated soak only after BF-20..24. Current `base_faction_soak.rs` covers 12 target factions by replacing one of six baseline seats, rotates the replaced seat by seed, and replays each seeded game twice; it is not the BF-25 18-faction all-pairs matrix. Extend or add a versioned harness that explicitly covers all faction pairs in both combat/seat positions, records game errors and replay identity, and bounds runtime. Then assert every row 2–8 for the twelve planned factions has no ledger gaps and no `blocked()` rows, gather the independent frontier exit review, and write the milestone report.

The safe immediate package sequence is therefore: accept the active faction timing/invasion/production WIP; close the four printed asset gaps or record an explicit accepted limitation that prevents BF exit; then BF-20, BF-21, BF-22, BF-23, BF-24, BF-25 in order. BF-23 bounds, BF-22 model compatibility, and BF-25 completion remain gated by saved artifacts and independent review, not by source edits alone.
