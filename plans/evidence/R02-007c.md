# R02-007c - start a table from the window, and say what the files are

## Why this package exists

The operator tried R02-007b and could not use it. Their words, verbatim:

> not sure how this is supposed to work, i cant set up a game in the replayer because there is no button
> for choosing setup, i can't load the regular profiles, but a session or a project and i cant tell what
> those are supposed to be. your command straught up errors out

All three are fair, and the third was my fault twice over: I told them to open a file that only exists
after running the command before it, and when it was missing the program answered with a usage line.

The deeper one is the first. R02 was spec'd and built as a *replayer* - open a recording, fork it, take a
seat - and I treated "start a table" as somebody else's job (`ti4-review simulate`, then open the file).
The reviewer's own window has had "Choose checkpoint…", "Choose map pool…", "Seed", "Faction rotation",
profile table, "Temperature", "Structured diplomacy" and **"Load starting table"** for its whole life, so
the operator was looking for those words in the second window and finding two buttons named after file
formats. A replayer you cannot start a game in is a viewer with extra steps.

## What changed

**Starting a table is now in the window.** `Replayer::start_table` does what the reviewer's button does -
the same `SimulationConfig`, the same checkpoint, map pool, seed, faction rotation, profile table,
temperature and structured diplomacy, in the reviewer's own labels and tooltips - and then keeps the seats
controllable, which the reviewer cannot. With nothing open the setup form *is* the window, with three
paragraphs saying what a table, a recorded game and a replayer file are; with a table already open the
same form opens as a floating panel from "Start a table…". Tick "Take seat 0 now" and the engine stops at
seat 0's first decision; leave it unticked and the learned policy plays every seat until a chip is
toggled.

**A table has a project before it has a recording.** `ReplayerProject::live_table` builds the source
timeline out of what the table *is* - inputs, checkpoint and map-pool hashes, content corpus, seating from
the branch's own header - with the session path left empty, because nothing has been recorded yet, and
`Origin::Live` on branch-0 so the file does not claim the branch was imported from something. It is
`verified` and `playable` like any root: the table is not a claim about somebody else's game, it is the
game, in this process.

**The two kinds of file are named after what they are.** "Open recorded game…" (a `.ti4review.json`: one
game, frame by frame) and "Open replayer file…" (a `.r02.json`: inputs, branches, answers - a recipe, and
what Save writes), each with the distinction in its tooltip, plus a paragraph in the welcome panel. The
internal words are still in the tooltips, because the operator also has 13 GB of files named the old way.

**A missing path says so.** `ti4-replayer some/file` on a file that is not there now prints what it
expected, how to start a table with no arguments at all, and the exact `ti4-review simulate` command that
produces a forkable recording - instead of the usage line.

## Deliberate limits, stated rather than discovered

- **Saving a table writes the replayer file, not an R01 session.** A recording of a hand-played table
  needs `LiveBranch::into_session()`, which joins the branch thread and so ends the table; that deserves
  its own button and its own words ("finish and record"), not a side effect of Save. Until then, a table
  saved here keeps its inputs, branches and every answer - enough to reproduce it - and the window says so
  in the status line at start.
- The setup form is not persisted in `replayer-settings.json` (it defaults to the example checkpoint and
  pool when they exist). R01's settings are still never read or written by this app.
- Frames still cross on the feed and the game still never leaves its own thread; starting a table uses
  `LiveBranch::start` exactly as the tests do, so "the window does what the headless shell test does" is
  literally true.
- `table_header` waits up to 120 s for the branch to report its seating, keeping frames published during
  the wait, and fails with the branch's state if it never does. The wait is on the UI thread, like the
  reviewer's own table load, which does its setup synchronously too.

## Verification

- `cargo clippy -p ti4-replayer --all-targets --no-deps -- -D warnings` exit 0 (compiles the bin, so the
  whole window is type-checked).
- `cargo test -p ti4-replayer --lib` 34 passed.
- New test `a_live_table_is_a_project_before_it_is_a_recording` in `tests/project.rs`: opens the reviewer's
  starting table, builds the live-table project from it, verifies inputs, asserts the branch is playable
  with an empty prefix, and asserts the saved file still says `Origin::Live`.
- **Integration suite initially blocked, not skipped**: the operator's replayer window was open, holding
  `target/debug/ti4-replayer.exe`, so cargo could not replace it ("Access is denied") and every
  `cargo test` that builds the package's bin failed. The suite was re-run into a separate target dir, so
  the running window was never killed; results are appended below.

Full suite, run with `CARGO_TARGET_DIR=target/verify` while the operator's window held the debug
executable (nothing they had open was killed):

```text

                                = 105 passed, 0 failed
cargo clippy -p ti4-replayer --all-targets --no-deps -- -D warnings  -> exit 0

```
