# R02-007e - remember the table, and a ledger for three bugs I did not guess at

## What was asked

Two things arrived together:

> l1z1x agents doesn't work
> transactions with hacan not possible, generally diplomacy buggy
>
> actual reviewer issue (small): last games profile map and settings should be kept as default

The second is small, precise and was fixed. The first three are one report about playing the game and are
recorded, not guessed at - see the ledger at the bottom.

## The remembered-settings defect

R01 already remembered the checkpoint, the map pool, the profile table, the temperature, structured
diplomacy and the last session opened. Two fields were not in that list, and one of them was worse than
missing: `ReviewApp::new` restored everything it loaded and then said

```rust
    seed: "42".to_owned(),
    rotation: 0,
```

so the seed and the faction rotation were thrown away on every launch. That is not a cosmetic slip: seed
and rotation decide which faction sits where, so "open the reviewer again and continue the run you were
watching" silently described a different game. Autosaved files are named `autosave-<seed>-rotation<N>-…`,
which is how the operator can see the mismatch from the file names alone.

Fixed by putting `seed` (text, because it is edited as text and a leading zero is somebody's idea of a
seed) and `rotation` into `ReviewerSettings`, restoring them at startup through `normalize_seed`, which
falls back to `"42"` when the remembered value is blank rather than showing a field that refuses to
parse.

The replayer had the same defect twice over: its window settings (`out/replays/replayer-settings.json`)
remembered panel open-flags and the last project, and its setup form remembered nothing at all - every
launch started from the example inputs in `examples/reviewer/`. And `ReplaySettings` was rebuilt from
`..Default::default()` on every write, so even the window's own size never survived a session.

Now `SetupDefaults { checkpoint, map_pool, seed, rotation, profile_table, temperature, diplomacy }` is
part of the replayer's settings; `SetupForm::remembered` opens the form with it, field by field, falling
back to the shipped examples where nothing has been remembered; and `persist` writes the form and the
window's real size back. `remember_setup()` runs **when a table starts**, not only on a clean exit - the
point is to survive the crash, and a window that dies at frame 200 should still open tomorrow with the
same checkpoint.

Two decisions worth stating:

- **A remembered path that no longer exists is still shown.** The point of remembering is to save typing
  a 90-character checkpoint path, and a moved file is easier to fix when the field shows what it was.
  Only a blank memory is skipped, because a blank is not a mistake, it is nothing remembered.
- **The two settings files stay separate.** `SETTINGS_PATH` is asserted not to contain `reviews`, and
  that assertion still holds: opening a replayer must not change how the reviewer looks tomorrow.

Compatibility: both files use container-level `serde(default)`, so a file written before these fields
existed loads and keeps what it does know (a new test asserts exactly that, and that a seed of `"007"`
comes back as `"007"`). The reverse - a new file read by an older build - hits `deny_unknown_fields`, and
both loaders already treat an unparseable settings file as "use the defaults, say so in the status line",
so the worst case is a forgotten window size, not a refusal to open.

### End to end, in the file itself

`target/release/ti4-replayer.exe` was started, left for 15 s and closed with `CloseMainWindow()` (a
killed process never reaches `on_exit`, which is how the first two attempts wrote nothing). The file
it wrote:

```json
{
  "window_width": 1720.0,
  "window_height": 980.0,
  "players_open": true,
  "decisions_open": true,
  "branches_open": false,
  "last_project": null,
  "last_branch": null,
  "setup": {
    "checkpoint": "D:\Projects\ti4-engine-rs\examples/reviewer/checkpoint-473312/slots.json",
    "map_pool": "D:\Projects\ti4-engine-rs\examples/reviewer/full_np8_12_holdout.json",
    "seed": "4242",
    "rotation": 0,
    "profile_table": "Learner",
    "temperature": 0.5,
    "diplomacy": false
  }
}
```

`branches_open: false` came *in* from the file the operator's older window had written, which is the
other half of the proof: it reads what is there and writes it back, rather than resetting the window
towards the source tree every session.

While in the setup form: leaving structured diplomacy off now says so in one line under the checkbox -
*"Off: nobody at this table can offer a deal or a transaction."* - because the default being off is not
a quieter game, it is a different one, and one of the three reported bugs is probably that.

## Ledger: the three playing defects, recorded rather than guessed at

Nothing below was changed. Each line says what was checked in code and what is still unknown; the honest
state is "reproduced: no", and a guess-fix against a live table the operator was driving would have been
worse than useless.

1. **"transactions with hacan not possible"**
   Checked: the replayer's setup form and `SetupDefaults` both default `diplomacy: false`, and the engine
   gates proposals on `state.diplomacy.enabled` (`crates/ti4-engine/src/diplomacy/window.rs:62`), which
   also holds the per-pair budget. A table started without structured diplomacy cannot transact with
   anybody, Hacan included - that is the first thing to rule out, and it is a default I chose, so if that
   is what happened the default is wrong and should follow R01's last-used value (it now does).
   Unknown: whether the operator had diplomacy on; whether the recipient was a manual seat or a policy
   seat; whether an option existed and did nothing, or was never offered. Those are three different bugs.
2. **"generally diplomacy buggy"**
   Checked: `crates/ti4-engine/src/diplomacy/` has `candidates`, `promises`, `relations`, `transfers`,
   `window`, and `signals.rs` carries an error `this pair has already initiated contact this turn` - so
   one proposal per pair per turn is a rule, not a fault, and "the second thing I tried did nothing" may
   be the rule biting. Unknown: what was actually attempted and what the window said.
3. **"l1z1x agents doesn't work"**
   Checked: L1Z1X content exists in the engine (`faction_abilities.rs`: Cybernetic Enhancements,
   Assimilate, Harrow; `l1z1x_mech` / Anihilator in the unit registry), so this is not an absent faction.
   Unknown: "agents" - the leader agent, the faction ability trigger, or a seat on Manual never being
   asked? No engine or replayer change was made on the strength of the word "agents".

Scope note: `crates/ti4-engine/**` is not in R02's editable surface. If any of these turn out to be
engine faults, they need their own work item with a failing engine test; if the engine offered something
the window did not surface, that is R02's and belongs in R02-008.

To reproduce I need four facts, and the fastest form is the saved files: which `.ti4review.json` /
`.r02.json` the table is in (it carries the seed, rotation, profile table, diplomacy flag and every
decision in it), whether the seat in question was on Manual at the time, what was clicked, and what the
window said. The first alone usually answers the rest.
