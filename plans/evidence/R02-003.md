## Outcome

`crates/ti4-replayer/src/live.rs`: one running branch. A [`LiveBranch`] owns a thread that builds the
reviewer's own `LiveReview` and never lets it escape; every command the user issues goes through one
`Gate` (a mutex and two condition variables) that the same thread consults from inside
`Table::ask`. A manual seat parks there — inside the engine's own question, before `settle` — and
nothing mutates while it waits.

## The plan's mechanism could not work, and the numbers that say so

`plans/R02_REPLAYER.md` says "Keep execution single-threaded. Before every `Game::step()`, inspect
`Game::legal_options()`", and separately allows a different mechanism "unless measurement proves
bounded UI batches inadequate". This package is that measurement. All numbers below come from the
committed example bundle and map pool, seed 4242, rotation 1, temperature 0.5, `ProfileTable::Learner`,
every seat Manual, every ask answered with its first offered option, using the code in this commit:

| Engine steps | Asks the gate saw | Steps that raised ≥2 asks | Worst single frame | Events dropped by the bound |
| --- | --- | --- | --- | --- |
| 120 | 158 (1.32 / step) | 17 | frame 118 raised **7** | 0 of 4,096 |
| 400 | 506 (1.27 / step) | 52 | frame 370 raised **10** | 0 of 4,096 |

Sessions ended at 121 and 401 frames (frame 0 plus the steps) with `outcome = InProgress`, so these
are ordinary play, not an error path.

Consequences, each of which the plan's mechanism cannot satisfy:

1. **A step-boundary probe is not a pause before the seat's next choice.** 17 of 120 steps (52 of 400)
   raise several questions; a single frame raises up to ten. `legal_options()` before the step is silent
   about all but the first, so a Manual seat would be answered by the policy from the second ask on —
   exactly the "reactions, transactions, combat, payments, production, and agendas" the locked section
   says must be interruptible.
2. **The probe cannot see most of what it would pause for.** `legal_options()` never inspects
   `Game::trade`, and `Game::step()` dispatches trade, voting, aftermath, diplomacy, agenda talks,
   tokens, scoring and `technology::start_turn` (itself a loop) before asking anything; 116
   `Table::ask`/`ask_seeing` call sites live in 22 engine modules.
3. **The only authoritative moment is the decorator being asked.** That is where every decision —
   however nested — necessarily passes.

So the pause is taken inside `Table::ask`, which needs a second thread to answer it. Execution is
still single-threaded in the sense that matters — exactly one thread ever touches `Game` — and
abort-and-retry stays rejected (`Game` is not `Clone`; the open windows, `prepared_turn_seq`,
`event_sequence` and galaxy live on `Game`, so a retried step could not be reconstructed).

Measured delivery, which also settles R02-002's open gap: **all 158 and all 506 asks arrived through
`Decider::choose_seeing`; none through the viewless `choose`.** `Gate::delivery()` counts the two
entry points precisely because `SeatObservation::bind` is `pub(crate)` and no outside test can build a
bound observation by hand. A live test asserts `bound > 0` after real play, so the bound path is now
proven by the engine rather than by argument.

## `Gate` semantics

One mutex holds the seat modes, the pending offer, the answer for it, the goal, the pause flag and the
lifecycle state, so a mode change and a pending offer can never disagree. Commands are not messages:
the UI thread calls the gate and gets its result synchronously.

| User action | Engine effect | Recorded |
| --- | --- | --- |
| Seat on `Auto` | policy answers | `Policy` |
| `Manual`, panel open, answer submitted | engine validates through `Table::settle` | `Human` |
| `Let bot choose this decision` | policy answers this one; seat stays Manual | `DelegatedToPolicy` |
| `Return seat to Auto` while its panel is open | panel closes, policy answers it | `Policy` + `ModeEffect::ReleasedBot` |
| Changing a different seat | panel untouched | `ModeEffect::Changed` |
| Stale fingerprint / invented option / duplicate | **nothing**: the panel stays open and the engine stays parked | `SubmitOutcome::{Stale, NotOffered, Duplicate}` |
| `pause` | goal ends on the next step boundary | `LiveEvent::Batch` |
| `stop` | no further advance accepted; a pending panel is **not** discarded | `LiveState::Stopped` |

States are exactly the plan's six: `Ready`, `Running`, `WaitingForHuman`, `Stopped`, `Completed`,
`Failed` (`Failed` also covers the reviewer's own `SafetyLimit`/`EngineFailed` outcomes, which are not
playable branches).

### Deadlock-freedom, stated and enforced

The only sim→UI channel is `sync_channel(MAX_QUEUED_EVENTS = 4096)` and is written with `try_send`; a
full queue increments `Gate::dropped_events` instead of blocking. A simulation blocked on a UI that is
blocked waiting for the simulation is the one way this design could hang, and measured drops were 0.
Nothing the UI waits on is behind that channel: a pending offer, the state, the seat modes, the answer
log and the defensive counters all come from the gate, and `wait_until_parked` /
`wait_until_idle` read the gate, not the queue. `Drop` therefore never joins — it only asks the thread
to unwind, because a thread parked on a question cannot be answered by an owner that is dying.

### Handing the game back

`LiveReview` is **not** `Send` (it holds `Rc<RefCell<Vec<DecisionDetail>>>` and `Box<dyn Decider>`), so
it cannot cross the thread boundary and this package does not pretend otherwise with `unsafe`. The
thread builds it, owns it, and on shutdown sends the finished `ReviewSession` — plain owned data — on
a terminal channel of one item; `LiveBranch::into_session()` joins and takes it. A test asserts the
session agrees with the events about how far the branch got (frame counts, seed, rotation).

## Tests (`crates/ti4-replayer/tests/live.rs`, 8, all engine-driven)

Inputs are the committed example bundle and pool; there is no skip path, and the helper names a
missing input as a broken checkout. Every wait is bounded (120 s) so a pause that never happened
fails in minutes rather than hanging.

| Test | Proves |
| --- | --- |
| `a_manual_seat_parks_before_any_mutation_and_play_resumes_when_answered` | the branch parks (`WaitingForHuman`), the panel names a physical seat; 120 ms later the frame count has not moved and the fingerprint has not drifted; **reading the gate does not answer it**; submitting the offered option is `Accepted`, the panel closes, the engine resumes, and the answer log says `Human` |
| `nested_asks_inside_one_engine_step_each_get_their_own_panel` | over 120 steps some engine frame raises several asks; within one frame the asks are numbered 0..k and every one has a **distinct fingerprint** (so a nested prompt is never mistaken for a repeat); and `choose_seeing` delivered them (`bound > 0`) |
| `a_stale_or_invented_answer_is_refused_and_the_panel_stays_up` | a click aimed at an already-answered panel is `Stale { current }`; an invented id is `NotOffered { offered }` matching the panel exactly; the pending fingerprint is unchanged after both refusals; then the real answer is accepted and the engine reaches a third decision |
| `switching_the_waiting_seat_to_auto_lets_its_bot_answer_it` | changing *another* seat is `Changed { previous: Manual }` and leaves the panel alone; turning the waiting seat over to Auto is `ReleasedBot { previous: Manual, choice: <that fingerprint> }`, its panel closes, and the log records that seat's answer for that offer as `Policy` |
| `delegating_answers_one_decision_and_keeps_the_seat_manual` | `delegate_pending` returns the parked actor, the log entry for that exact fingerprint is `DelegatedToPolicy`, the seat stays Manual, and the same seat is asked again later with a different fingerprint (so delegation is one-shot, not a mode change) |
| `a_run_of_n_steps_stops_at_exactly_n_when_every_seat_is_auto` | runs of 1, 3 and 7 steps report exactly 1, 3 and 7 frames with nothing parked, and the handed-back session has exactly frame 0 + 11 frames with the configured seed and rotation |
| `pause_ends_the_goal_on_a_step_boundary_and_stop_is_terminal` | `pause` ends a 10,000-step goal early (state `Ready`, not `Stopped`); a following 3-step goal runs exactly 3 frames, so the branch is alive; `stop` makes the state `Stopped`, `run` returns `NotRunnable(Stopped)`, and no further frame is emitted |
| `the_same_command_script_produces_the_same_session` | the same script (three separate `Steps(10)` commands) twice produces identical per-frame and per-decision digests, and identical to a single `Steps(30)` command — so the gate and the batching do not perturb the engine's ordering or RNG |

Plus 19 unit tests in `control.rs` / `decider.rs`, including the gate-level ones that the live path
cannot reach: a detached gate counts `unanswered` instead of parking, a queued answer for a different
offer is dropped and counted as `stale` (once, not twice), one-shot delegation keeps the seat Manual,
and the decorator's fingerprint equals the one `PendingManualChoice` would publish for the same
`Choice`.

## Deviations and judgement calls

1. **One simulation thread + `Gate`, instead of the plan's pre-step `legal_options()` probe.** Numbers
   and reasoning above; the plan's own escape clause covers it. The gate is where the plan's
   `ControlledDecider` priority order lives, and `ManualControl` (R02-001) is the state machine doing
   the accept/refuse decisions — no second copy of that logic.
2. **`AdvanceGoal` instead of R01's `AdvanceUnit`.** `Steps`, `NextRound` and `EndOfGame` are driven
   engine-step-by-engine-step, so every frame is reported and `pause`/`stop` land on a step boundary;
   `Decisions(n)` and `Actions(n)` are handed to `LiveReview::advance` unchanged so they keep R01's
   exact meaning. Those two report one `LiveEvent::Batch` rather than a frame event per step — the
   manual pause still happens inside them, only the incremental frame feed does not.
3. **Shutdown while parked answers from the policy, counted.** `shutdown_fallbacks` exists because
   there is no way to abandon an `ask` mid-step; a branch that ended that way is not a clean playable
   branch and the counter says so. `stop` deliberately does **not** interrupt a park: the plan is
   explicit that stop is a step-boundary operation and does not discard the pending choice.
4. **`LiveSession` hand-back instead of handing back the `LiveReview`** — `Send` is unimplementable
   here without `unsafe`; see above.
5. **Goals queue.** An advance issued while one is running is taken after it finishes; a requested but
   not-yet-started goal is replaced by the newer one. The loop keeps `Running` when a goal is already
   queued (`Gate::goal_queued`), because flicking to `Ready` between back-to-back commands reads as
   "this branch has come to rest" — that flicker was a real bug this suite caught.
6. **Pending offers carry `faction: None`.** The R01 hook names only the physical `PlayerId`, and the
   field is documented as presentation-only; the GUI fills it from the session manifest, which already
   carries factions. Control decisions never read it.
7. **`ManualControl::delegate_seat_once` added** to `control.rs` (an R02-001 file) for the delegation
   clicked a moment *before* the engine reaches the ask, which `delegate_pending_once` (panel open)
   could not express. It is one-shot for the same reason.
8. **`ManualInbox` kept** alongside the live park. The live branch never needs it; R02-004's replay
   prefix does (answer without asking), and the detached gate uses it for the fallback-path unit
   tests. Documented as such rather than deleted and re-added later.

## Verdict

**ACCEPTED.** A live branch can be stepped, paused at any decision the engine actually raises
(nested ones included, with the count measured rather than assumed), answered by a person through the
engine's own validation, delegated once, released to a bot, paused, stopped, and handed back intact;
refused answers change nothing; and the same command script produces the same game. The plan's
single-threaded pre-step probe is rejected on measurement, recorded above with its numbers.
