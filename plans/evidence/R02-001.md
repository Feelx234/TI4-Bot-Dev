## Measurements behind those decisions (read-only, no engine or R01 edits)

Source: `out/reviews/pruned-diplomacy-seed11-t05.ti4review.json` (69,183,276 bytes, 603 frames,
schema `ti4-review-session`, outcome `in_progress`), analysed with a throwaway script under the
session temp directory. `decision_count` per frame is `Game::table.log.len()`, i.e. the engine's
own settled-answer count, so these are engine facts rather than trace artefacts.

- 670 settled decisions across 602 engine steps.
- **37 of 602 steps (6.1%) settled more than one decision; the maximum observed was 8** in a single
  step (`action phase` → `Construction: a structure or a production` → `produce in 10 (6 left)` →
  `pay 1 more resources` → …). So the plan's "one engine step consumes at most one generated
  choice" is false as written, and its regression test cannot be written as a pass condition.
- 0 synthetic trace rows in this particular session (all 670 rows have `path == "seeing-mlp"`);
  checkpoints carrying arena fact-version-7 plans do emit synthetic rows (`fleet decision`,
  `plan stopped`, `package|…` ids), which is why `ReplayRecord` is a separate authoritative type
  instead of a reuse of the reviewer's `DecisionDetail`.
- Plain-JSON cost: 114,731 bytes/frame here, 183,036 bytes/frame in
  `out/reviews/autosave-234-rotation0-learner.ti4review.json` (249,111,965 bytes / 1,361 frames).
  Against `MAX_SESSION_BYTES = 1 GiB` — checked on the *plain* serialization in
  `crates/ti4-review/src/lib.rs` — that is roughly 6k–9k frames, i.e. one ordinary game. Inheriting
  that bound with 128 branches per project is not satisfiable if branch frames carry state
  snapshots. **Open question carried forward to R02-005.**

Engine facts read from source (`crates/ti4-engine/src/`), not measured:

- `Game::step()` calls `self.legal_options()` and asks exactly that choice — but only after
  dispatching `secondary`/`event_scoring`/`scoring`/`tokens`/`voting`/`aftermath`/`diplomacy`/
  `agenda_talks`/**`trade`**/`tactical` and `technology::start_turn`. `legal_options()` never inspects
  `self.trade`, so a transaction step asks a choice the pre-step probe cannot see.
- `technology::start_turn` receives `&mut Table` and loops: Psychoarchaeology asks until the seat
  declines, Transit Diodes asks up to four times.
- 116 `table.ask`/`ask_seeing` call sites across 22 engine modules take `&mut Table` (combat,
  invasion, production, fleet, leaders, action cards, secrets, relics, …).
- `Game` is not `Clone`, and the open windows (`tactical`, `secondary`, `trade`, `scoring`,
  `voting`, `aftermath`), `prepared_turn_seq`, `event_sequence` and `galaxy` live on `Game`, not in
  `GameState`. A step cannot be aborted and re-run from a snapshot, and a saved frame cannot be
  resumed. This is what rules out the abort/retry pause mechanism and forces the parked-decider
  design.

## Design points worth a reviewer's attention

- **`ChoiceFingerprint` binds actor, prompt, ordered `(id, kind)` pairs and the typed context**, per
  the plan, and excludes branch, frame, ask index, labels, payloads, previews, scores and
  probabilities. Labels/scores are presentation; branch/frame/ask are provenance. Excluding frame
  identity is deliberate — it is what lets `ReplayRecord::matches` recognise a rebuilt offer.
- **Every pre-image field is length-prefixed** (`len:bytes`). Test
  `field_boundaries_cannot_be_spliced_into_the_same_fingerprint` covers the splicing case
  (`"a|decline"` + `x` versus `"a"` + `"decline|x"`).
- **Refusals never consume the pending choice.** `SubmitOutcome::{NoPendingChoice,Stale,NotOffered,
  Duplicate}` all leave `pending` intact, and `Stale` returns the live fingerprint so a panel can
  redraw instead of guessing.
- **`Duplicate` versus `NoPendingChoice`.** After an accepted answer the control remembers only that
  choice's fingerprint, so a second identical click reports `Duplicate` while a click aimed at a
  choice that was never on screen reports `NoPendingChoice`.
- **Seat keying is `PlayerId`, never faction.** `PendingManualChoice.faction` exists for the panel
  only and is excluded from the fingerprint.
- **`set_mode` reports what it did to a waiting panel** (`ModeEffect`), so the pending actor's own
  switch to Auto releases its choice to the bot while a change to any other seat cannot.
- **Delegation is one-shot** (`SeatControl::take_delegation` removes) and setting a seat to Auto
  drops a delegation it never got to use.
- **Bounds refuse rather than truncate**: `MAX_BRANCHES_PER_PROJECT = 128` (source timeline
  included, so 127 children), `MAX_OFFERED_OPTIONS = 1024`, empty offers rejected.

## Plan text now contradicted (needs an operator nod before R02-003)

`plans/R02_REPLAYER.md` still says, and these four lines now conflict with the decisions above:

1. *"Keep execution single-threaded. Before every `Game::step()`, inspect `Game::legal_options()`."*
   — `legal_options()` cannot see the transaction window, and cannot see nested asks at all.
2. *"Add a regression test that one engine step consumes at most one generated choice."* — false in
   the engine (6.1% of steps, max 8). It should become a *documented engine fact* plus the
   `ask`-within-frame invariant in these types.
3. *"Do not add worker-thread deciders/channels unless measurement proves bounded UI batches
   inadequate."* — the clause is now met: one thread owns `LiveReview`/`Game` and
   `ControlledDecider::choose` parks on a rendezvous with the UI. `Game` never crosses the thread;
   only published frames and snapshots do. The plan's *"Rc<RefCell<_>> is acceptable on one thread"*
   still holds for the policy wrappers, since they are created and used on that same thread.
4. *"R02-004 … one narrow engine invariant test"* — dropped under the frozen-engine rule.

Proposed corollary for R02-003, for the record: because the engine may have applied earlier choices
of the current step when it parks, the thread publishes `game.state.clone()` with each parked
choice, so a nested prompt shows the position *after* the choices already taken in that step rather
than a stale pre-step frame.

## Judgment calls a reviewer should look at

- `#![allow(clippy::module_name_repetitions)]` at the top of `control.rs`. `ControlError`,
  `SeatControl` and `ManualControl` are the names callers should see; renaming them to satisfy a
  naming-shape lint would read worse at the call site. If the lint does not actually fire on them,
  the attribute is dead weight and should be deleted.
- `MAX_BRANCHES_PER_PROJECT` is `u32` rather than `usize` so the branch allocator compares without
  a cast; `MAX_OFFERED_OPTIONS` stays `usize` because it is compared against `Vec::len`.
- Frame and ask indices are `u64`/`u32` in these types rather than `usize`, so the project file's
  number widths do not depend on the host.
