# R02-007d - the reviewer's sheets in the replayer, and a fork that actually forks

## Why this package exists

The operator used R02-007c and listed six things wrong with it:

> - there is still not enough game state information to judge a play, the left panel of the reviewer needs
>   to be replicated completly, with regards to infoamtion content
> - branching does not work at all
> - setting other seats to manual mid game does not work
> - the displayed gamestate is not moving with the live tip which is extremely confusing
> - there is way to little information displayed on the decision panel and for longer lists it gets cropped
> - systems need to be referenced by planets inside as well as tile number

Two of those are defects with a single line behind them, one is three defects stacked, and three are the
consequence of building a second window around abbreviations of R01's panels instead of R01's panels.

## The defects, each reproduced before it was fixed

### The board never moved with the game

`ReplayApp::record_frames` appended the new frames and *then* asked `at_tip()` whether the reader had
been watching the newest one. `at_tip` compares the viewed index against the last index, and appending
had just moved the last index - so the answer was "no" every single time a frame arrived, and the view
stayed wherever it was when the first batch landed. For a table started in the window that is frame zero,
for the whole game, while the timeline counted up beside it.

The question is now asked before the frames land. Reproduced first:

```text
start viewed=Some(0) frames=9 viewed=Some(0) at_tip=false   <- before
start viewed=Some(0) frames=9 viewed=Some(8) at_tip=true    <- after
```

Pinned by `app.rs::a_reader_at_the_tip_is_carried_along_by_the_branch` and, end to end against the
engine, by `table.rs::the_board_follows_a_table_that_is_playing`, which also asserts the other half:
a reader who has scrolled back to frame 1 is *not* dragged forward by the next batch.

### Branching did not work at all - three separate reasons

**1. A live table's project says it has zero frames.** `ReplayerProject::live_table` starts branch-0 at
`frames: 0` (nothing has been recorded yet), and nothing ever updated it as the table played.
`ReplayerProject::fork` refuses a frame at or past the end of the parent, so *every* Play from a table
started in the window was refused:

```text
play_check: Ok(())
plan: Refused("branch-0 ends at frame 0, so it cannot fork at frame 5")
```

`ReplayerProject::note_frames` is new and `record_frames` calls it, so the count the project keeps
follows the frames the branch has actually produced. `app.rs::frames_arriving_grow_the_branch_the_project_knows_about`.

**2. A live branch's answers only reached the project on save.** The fork's prefix script is built from
the *project*, and `fold_branch_into_project` ran only from `save_project`. So a fork planned before a
save replayed a script of nothing. With every seat on Auto that reproduced by luck - same seed, same
policy, same stream - which is why the shell tests never saw it. With a seat on Manual the rebuild had
no answer for the first decision and parked, waiting for the operator to answer the whole game a second
time, with a spinner on screen saying "Rebuilding and checking the prefix…" forever:

```text
held 49 frames, 49 records
script answers = 0
REBUILD PARKED on seat0 · spend a strategy token to produce at home · frame 48 ask 0
```

`Replayer::play` now folds before it plans.

**3. The prefix was cut one frame short of the fork.** A decision is stamped with the number of frames
that existed when the engine asked it, so the answers stamped `F` are the ones the step that *produces*
frame `F` consumes. `ReplayerProject::prefix` cut ancestors at `record.frame < fork_frame`, which left
the last step of every prefix unanswered - the same park, one decision later:

```text
script answers = 47   (of 49)
REBUILD PARKED on seat0 · ... · frame 48 ask 0
state=WaitingForHuman replayed=47
```

The cut is now inclusive, and `store::own_answers` moved with it (`> fork_frame` rather than `>=`), so
the two halves still partition the record set exactly once. With all three fixed:

```text
script answers = 49
state=Ready replayed=49 divergence=None
fork outcome: Ok((49, 49))
```

`table.rs::a_table_started_here_can_be_forked_from` and `table.rs::a_fork_replays_the_answers_a_person_gave`
(which answers three decisions by hand, always the last option offered, so a prefix that is not replayed
diverges). `project.rs::a_prefix_inherits_up_to_the_fork_and_not_beyond` was updated, deliberately: it
had pinned the off-by-one.

### Seats set to Manual mid-game

The gate path itself is sound - `table.rs::a_seat_flipped_while_the_table_runs_is_asked` flips five seats
while the branch is running and the engine parks on one of them within the same goal, with zero
`unanswered` fallbacks, and `a_seat_flipped_while_another_is_parked_leaves_that_panel_alone` shows the
open panel surviving it. What was broken around it:

- **A seat taken during a rebuild went to the dead branch.** `ReplayApp::attach` was only called when the
  rebuild *finished*, so between pressing Play and the fork going live the chips talked to the gate of
  the branch that had just been left behind, and the fork started with the modes captured at the button
  press. New `ReplayApp::attach_handle` swaps the gate without touching the frames, and `play` calls it
  as soon as the fork's thread exists.
- **The chip claimed success it could not deliver.** A branch that is stopped, completed or failed will
  never ask anything again; the status line said "it will be asked at its next decision" anyway. It now
  says what state the branch is in and that forking from a frame is how to play it on.
- **A seat that has passed looks identical to a seat that is broken.** The chip now carries `· passed`
  and `▶` for the seat currently being asked, and the tooltip explains that the next question for a
  passed seat comes in the round after this one.

### The panels

R01's left sheet is ~590 lines of accumulated detail; the replayer's was 40 lines of names, points and
four counts. R01's right sheet carries the action summary, every decision with its typed context, every
option with its payload, consequence preview and feature/weight/contribution grid, the engine events and
the selected system; the replayer's carried prompts and a rank line.

Both moved, unchanged, into `crates/ti4-review/src/panels.rs` as `players_sheet` and `decision_sheet`
(and `diplomacy_sheet` with them). R01's `player_panel` and `decision_panel` are now the panel chrome
plus one call each, and the replayer calls the same two functions. This is the deferred R02-006d that
R02-007c named as the next package. The sheets draw *contents*, not panels, because the frame, the width,
the collapsing header and the light theme are where the two windows legitimately differ.

The manual-choice list no longer competes with the sheet below it for the panel's leftover height: it
gets a bounded scroll of its own (half the panel, clamped), options wrap instead of being clipped, and
each carries its id, kind and structured payload on hover. That is the cropping.

### Systems named by what is inside them

`view::system_label` spells a system as `14 · Archon Ren/Archon Tau` (or `43 · Supernova` for a tile with
no planets), and `view::annotate_systems` rewrites every bare tile number in a sentence the engine wrote:
`activate 14`, `commit ground forces in 75`. Only digit runs that name a tile of *this* game's board and
that stand on their own are rewritten, so `produce 2x fighter for 1` and `sol_75x` are left alone -
pinned by `presentation.rs::only_numbers_that_name_a_tile_are_rewritten`.

R01's wording is deliberately unchanged: `SystemNaming::TileOnly` for the reviewer, `TileAndPlanets` for
the replayer. R01's golden tests and its readers already know its labels.

The replayer's board also gained R01's seat row and its stroke legend, which were simply absent.

`crates/ti4-review/tests/panel_paint.rs` is new and is the answer to R02-007c's lesson that "105 tests
pass and none of them renders a pixel". egui runs a whole pass headlessly, so both shared sheets are now
actually painted against a real board and a real decision-bearing frame, and the frame is read back for
the marker egui paints over a duplicate widget id. `a_duplicate_id_is_seen_by_this_test` deliberately
clashes two headers, so the check is known to fire rather than assumed to.

## Not fixed here

- The window still has no automated proof of its *own* layout: `panel_paint` covers the two shared
  sheets, not `Replayer::ui`'s panel order. That remains an operator smoke pass.
- R01's semantic golden was run and is unchanged, but R01's pixels were not re-inspected; the sheet code
  moved byte-for-byte, and the only intentional R01-visible change is the per-option collapsing header
  gaining an explicit `id_salt` (it previously took its id from the option title, which two identically
  labelled options in one decision would have shared).

## Post-script: this package shipped a crash, and its own suite did not see it

The operator ran the build and got:

```text
PS D:\Projects\ti4-engine-rs> cargo run -p ti4-replayer
     Running `target\debug\ti4-replayer.exe`
thread 'main' (73148) panicked at crates\ti4-review\src\view.rs:1176:23:
range end index 0 out of range for slice of length 0
```

### Cause

Moving R01's panels into `ti4-review/src/panels.rs` moved them with their assumption intact: that a
`ReviewSession` carries its own frames. R01's does. The replayer's store deliberately hands out a session
*shell* per branch with `frames` emptied - `Store::import` and `Store::apply` both do
`shell.frames = Vec::new()`, because an R01 recording is hundreds of megabytes and a branch tree must not
multiply one - and the frames live in a list beside it. Two lines in the shared code reached into the
shell:

- `view::action_summary`: `session.frames[..=frame.index]` → *"range end index 0 out of range for slice of
  length 0"* (the operator's crash).
- `panels::players_sheet`: `&session.frames[frame.index - 1]` for the speaker-changed row → *"index out of
  bounds: the len is 0 but the index is 39"*.

The paint tests added in this very package missed it because they painted with `played()`, a session that
carries its frames. That is the same blind spot as the panel-order bug in R02-007c, one level deeper: the
fixture had the shape of R01 and the code was being run with the shape of the replayer.

### Fix

`panels::Sheets`, so a sheet is told where the history is instead of assuming it is inside the header:

```rust
pub struct Sheets<'a> {
    pub header: &'a ReviewSession,           // manifest, board, content
    pub frames: &'a [ReviewFrame],           // what to scan backwards through
}
```

`Sheets::whole(session)` is R01 - its frames really are its header's. The replayer passes
`Sheets { header: store.session(branch), frames: store.frames(branch) }`. `Sheets::previous` finds the
neighbour by `index` rather than by position, and `view::action_summary_in(frames, frame)` scans whatever
list it is given. Both scans are now total: a sheet handed a history that does not contain its frame loses
the row that depends on it and paints everything else, which is what a viewer does when it is confused;
aborting the process is not.

`action_summary(&session, frame)` still exists and delegates, so R01's call sites and its eleven existing
decision-view tests are untouched.

### The tests that would have caught it

- `ti4-review/tests/panel_paint.rs::the_sheets_paint_from_a_shell_and_a_separate_frame_list` - a real
  played session with `frames` emptied and the frames passed separately. Fails before the fix with the
  `len is 0 but the index is 39` panic; passes after.
- `...::the_sheets_paint_when_the_history_is_empty` - no history at all, the first frame of a fork. Both
  sheets paint.
- `ti4-replayer/tests/table.rs` now paints both sheets, for the last three frames of a real live table,
  through the store's own `session(branch)` / `frames(branch)`, and asserts the header really is empty
  (`"the store is supposed to keep the frames out of the header, or this test proves nothing"`). This is
  the window's path, with the window removed.
- `ti4-review/tests/decision_view.rs::scanning_a_supplied_history_answers_exactly_as_scanning_the_session`
  - for every frame of a played session, `action_summary_in(&session.frames, frame)` equals
    `action_summary(&session, frame)`, and `Sheets::previous` agrees with position `index - 1`. The split
    may move where frames come from; it may not change what R01 reads out of them.

Painting both sheets into one `paint()` call trips egui's duplicate-id check, because in the test they
share a `ui` while in the window they sit in side panels of their own; each sheet is painted separately,
which is also what `a_duplicate_id_is_seen_by_this_test` exists to guarantee is not a false comfort.

`control_bar` in the replayer's window went over clippy's 100-line limit once the chip tooltips landed, so
it is now three methods - `seat_chips`, `run_controls`, `play_control` - with the bodies unchanged.

is only answered in the sense that the same code now runs. Their eyes remain the acceptance gate.
